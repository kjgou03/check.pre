## 1. 결론: 양식·회의록과 맞는가?

**맞습니다.** 3차 회의에서 확정한 아이디어를 거의 그대로 구현했고, 양식이 요구하는 항목(특히 ④의 "환각 대응·근거 표시·재시도")을 이미 갖추고 있습니다. 다만 아래 ⚠️ 항목은 기획서에서 "계획"으로라도 언급해야 회의록과 어긋나지 않습니다.

### 회의록 ↔ MVP 대응표

| 회의록에서 나온 것 | MVP | 상태 |
|---|---|---|
| (3차) 확정 아이디어: 입력 → ①규정 조회 ②위반 가능성·확인 사항 정리 ③승인 절차 안내 | `rules` → 점검 4종 → `open_questions` → `required_approvals` | ✅ 1:1 대응 |
| (3차) 150억 추가 투자 예시: 현재 비중 + 추가 후 비중 계산 | `limits.single` — "현재 1.49% → 추가 후 1.52%" | ✅ 시나리오 1 그대로 |
| (3차) 제재·거래 제한 대상인지 | `screening.sanctions` (OFAC SDN) | ✅ |
| (3차) 내부 투자 한도 | `limits.single` / `limits.sector` | ✅ (섹터는 벤치마크 데이터 없어 "판정 불가"로 표시) |
| (2차) 애널리스트는 본인 보유 종목 보고서 금지 → 보유면 반려 | `conflicts.check` → RED + "준법감시부 신고 및 담당자 교체" | ✅ 시나리오 2 |
| (2차) 내부 규정을 저장해두고 AI가 필요할 때 조회 | 조문 단위 JSON + `rules.get_rule` | ✅ |
| (2차) KIC가 ESG 배제 원칙을 어겼다는 보도 | `screening.exclusion` + 모드 B 포트폴리오 스크리닝 | ✅ 시나리오 3 |
| (한 줄 결론) 담당자와 최종 결정자만 남기고 중간 절차를 AI가 | 판정은 코드, 최종 판단은 사람(고지문) | ✅ |
| (3차) **관련 법률 위반 여부** | 구조는 있음(`ACT-` 조문 ID), 조문 데이터가 비어 있음 | ⚠️ 법령 원문 입력 필요 |
| (3차) **미공개 중요정보 관련 문제** | 없음 | ⚠️ 기획서에 "확인 질문 + 거래제한(Restricted) 목록 대조"로 추가 권장 |
| (3차) **위탁기관 투자 지침 충족** | 없음 (내부 지침만) | ⚠️ "위탁기관 지침도 같은 조문 DB에 카테고리로 추가"라고 쓰면 됨 |
| (3차) **필요한 승인·검토 절차를 거쳤는지** | "안내"만 함, 거쳤는지 "확인"은 안 함 | ⚠️ 확장(결재 시스템 연동)으로 서술 |
| (1차) 운용 상태를 주기적으로 돌려 비율 초과를 잡기 | 모드 B는 배제·제재만 보고 **한도는 안 봄** | ⚠️ 쉽게 추가 가능 — 기획서엔 "분기별 자동 점검"으로 |
| (1차) 주식에 한정할 필요 없음(사모·대체·부동산) | 상장주식만 | ➖ 범위 밖 → ⑦ 확장성으로 |
| (1차) 역할별 에이전트가 토론하는 멀티 에이전트 | 채택 안 함 | ➖ 이유를 설명할 수 있으면 오히려 강점 (아래 Q&A) |

### 우리 문서에서 고쳐야 할 표현 (사실 확인 결과)

1. **"2025년 국감에서 지적" → "2025년 10월, 국회 기획재정위원회 김영진 의원실이 KIC 제출 자료와 SEC 공시를 분석해 공개"** 로 쓰는 게 정확합니다. 보도 내용: KIC가 자체 투자배제 테마(담배·석탄·대마·논란 무기·아동노동)인 **담배·석탄 기업에 약 1조 2,600억 원(8억 7,500만 달러)** 투자, 담배 투자는 2021년 12월 2,454만 달러 → 2025년 6월 2억 9,130만 달러로 증가.
   → 기사 원문을 열어 숫자를 직접 확인하고 부록에 출처로 넣을 것.
2. **"알트리아가 지적된 바로 그 기업"** — 보도에서 특정 기업명이 나왔는지는 확인하지 못했습니다. 원문 확인 전에는 "담배 업종 대표 기업"으로만 표현.
3. **석탄 기준**: 보도에 따르면 KIC는 석탄 매출 **50%** 이상 기업을 배제(NBIM은 30%). 우리 모의 지침 `IG-5-1`은 **30%**. → 기획서에 "모의 지침은 NBIM 수준(30%)으로 강화한 가정"이라고 밝히거나, 이 차이를 **"기준을 바꾸면 영향받는 종목을 바로 보여주는 기능"(확장성)** 의 소재로 쓰기. (2026년 국감에서 KIC가 기준을 강화했다는 보도는 검색으로 확인되지 않음 — 쓰려면 원문 확인 필수)
4. **단일 종목 한도**: 1차 회의는 "5%", MVP 모의 지침은 "3%". 기획서 전체에서 하나로 통일.
5. **"1.26조를 재현했다"** — 아직 실데이터로 돌리지 않았으므로 예선 기획서에는 **"공개 데이터(13F + 공개 배제목록)만으로 재현 가능함을 본선에서 검증"** 으로 쓸 것.

## 2. 슬라이드별 작성법과 초안

### 표지 (slide 1)
팀명·팀장·팀원만. 서비스명을 부제로 한 줄 넣어도 좋음.

### Summary (slide 2) — 상호평가에서 가장 먼저 읽히는 장

| 칸 | 초안 |
|---|---|
| 서비스명 | **PreCheck** — 국부펀드 투자 규정 위반 가능성 사전 점검 AI Agent |
| 문제·사용자 | 투자 실행 전 배제목록·제재·투자한도·이해상충 확인을 사람이 여러 자료를 따로 대조해 처리 → 느리고 누락 위험. 실제로 2025년 KIC가 자체 배제 테마인 담배·석탄 기업에 약 1.26조 원을 보유한 사실이 국회 자료로 지적됨. 사용자: 투자 담당자(입력), 준법감시·리스크 담당(검토), 위원회(최종 승인) |
| Agent 제안 | 투자안(기업·금액·담당자)을 넣으면 적용 규정을 찾고, 4가지 점검 도구를 실행해 **근거가 붙은 신호등 보고서 1장**과 필요한 승인 절차를 안내. 판정은 결정론적 도구가, LLM은 입력 이해·요약만 담당하며 요약도 코드가 근거와 대조해 검증 |
| 데이터·기술 | SEC 13F 보유내역, NBIM·Urgewald 배제목록, OFAC 제재목록, 한국투자공사법·내부 지침(모의) / Claude API(구조화 추출·요약), 조문 단위 규정 검색, Python 점검 도구 4종, Streamlit |
| 기대효과 | 사전 점검을 수 초 안에 근거 포함 보고서로. 분기별 포트폴리오 자동 스크리닝으로 사후 지적 예방. 사모·대체 자산, 결재 시스템, 규정 변경 영향 분석으로 확장 |

### ① 문제 정의 (20점)
양식 요구: 업무 문제, 현행 방식의 문제점, 주요 사용자, 업무 상황, 활용 시나리오, 필요성.

초안
- **업무 상황**: KIC가 해외 상장기업에 150억 원 추가 투자를 검토. 투자 담당자는 성장성·밸류에이션을 보고, 컴플라이언스 담당자는 ① 법률 위반 ② 제재·거래 제한 ③ 내부 한도·위탁기관 지침 ④ 미공개 중요정보 ⑤ 승인 절차를 확인해야 함. (3차 회의 역할 구분 그대로)
- **현행 방식의 문제점**
  1. 배제목록·제재목록·보유내역·규정을 **사람이 각각 열어 대조** → 시간이 오래 걸리고 누락 위험
  2. "왜 통과됐는지" **근거가 남지 않음** → 사후 설명이 어려움
  3. **사후에야 발견**: 2025년 10월 국회 자료 — 자체 배제 테마 담배·석탄에 1조 2,600억 원
  4. 개인 이해상충(담당자 보유 종목) 확인도 **수작업 신고·대조**
- **주요 사용자**: 투자 담당자 / 준법감시부 / 리스크관리부 / 책임투자위원회
- **필요성**: 국부펀드는 장기투자자라 규정·ESG 위반 한 번이 평판·손실로 직결(1차 회의 논의). 공공기관이라 "왜 그렇게 판단했는지" 설명 책임도 큼.

넣을 그림: **현행 vs PreCheck 업무 흐름 비교**(현행: 담당자 → 목록 대조 → 한도 계산 → 보유 신고 확인 → 위원회 / 개선: 담당자 → PreCheck → 위원회)

### ② 서비스 제안 및 차별성 (차별성 20점)
양식 요구: 서비스 개요, 핵심 기능, 입력 → Agent 수행 → 최종 결과물 흐름.

초안
- **한 줄**: "규정 준수 확인에 필요한 중간 절차를 Agent 하나로 줄여, 담당자와 최종 결정자 사이에 근거가 붙은 보고서 한 장만 남긴다." (3차 회의 피치 문장)
- **핵심 기능**
  - 모드 A 사전 점검: 배제 테마 / 제재 / 단일종목·섹터 한도 / 이해상충 → 신호등(🔴🟡🟢⚪) + 근거 + 필요한 승인 + 확인 질문
  - 모드 B 포트폴리오 스크리닝: 보유 전 종목을 목록과 대조 → 테마별 건수·금액
- **흐름**: 자유 문장 또는 폼 입력 → 투자안 구조화 → 적용 규정 조회 → 점검 4종 → 종합 신호 결정 → 요약 작성·검증 → 보고서(화면·Markdown 다운로드)
- **차별성** (범용 챗봇 / 단순 규칙 엔진과 비교)
  1. **근거 없는 판정은 만들 수 없다** — RED·YELLOW는 근거가 없으면 시스템이 거부. 문제없음(GREEN)에도 "무엇을 몇 건 대조했는지"를 남김
  2. **LLM은 판정하지 않는다** — 신호·숫자·승인 절차는 코드가 계산. LLM이 틀려도 판정은 바뀌지 않음
  3. **요약의 환각을 자동 차단** — 존재하지 않는 조항·근거에 없는 숫자를 쓰면 재작성, 그래도 안 되면 코드 요약으로 대체
  4. **모르는 것은 모른다고 표시** — 벤치마크 데이터가 없으면 "판정 불가"로 드러냄
  5. **같은 투자안도 누가 올리느냐에 따라 결과가 다름** — 담당자별 이해상충 (2차 회의 애널리스트 사례)
  6. **사전(투자 전) + 사후(분기 점검)를 같은 엔진으로**

넣을 그림: MVP 화면 캡처 `docs/screenshots/scenario1_altria_S002.png` (신호등 부분만 잘라서)

### ③ Agent 역할 및 Workflow (Agent 구성·설계 25점 — 가장 중요)
양식 요구: 역할·목표, 작업 계획, 정보 탐색·분석, 결과 생성 및 검증, **스스로 판단·수행하는 범위와 종료 조건**.

초안
- **역할·목표**: 투자 실행 전, 규정 위반 가능성을 빠짐없이 찾아 근거와 함께 보고하고 필요한 승인 경로를 안내한다.
- **Workflow (7단계)**
  1. 입력 이해: 자유 문장 → 기업·금액·담당자 추출(LLM), 보유내역과 대조해 종목 식별
  2. 계획: 필수 정보 확인, 적용할 점검과 규정 범주 결정
  3. 정보 탐색: 규정 DB, 배제·제재 목록, 보유내역, 담당자 보유 DB 조회
  4. 분석: 점검 도구 4종 실행 (이름 매칭, 비중 계산)
  5. 종합: 규칙으로 종합 신호 결정(RED 하나라도 → RED …)
  6. 생성: 3~4문장 요약 작성(LLM)
  7. 검증: 요약 속 조항 ID·숫자를 근거와 대조 → 실패 시 재작성
- **자율 범위**

  | Agent가 스스로 | 사람에게 묻는 것 | 절대 하지 않는 것 |
  |---|---|---|
  | 입력 해석, 기업 식별, 점검 실행, 요약 작성·재작성, 보고서 생성 | 필수 정보 누락, 이름이 비슷한 기업(동일 기업인가?), 미등록 담당자, 키워드 후보의 매출 비중 | 최종 승인·반려, 종합 신호 변경, 근거 없는 판정 |

- **종료 조건**
  - 필수 정보 누락 → 질문을 돌려주고 **중단**
  - 모든 점검 완료 + 요약 검증 통과 → **보고서 출력**
  - 요약 검증 2회 재시도 실패 → 코드 생성 요약으로 **보고서 출력**
  - LLM 장애·키 없음 → 정규식·템플릿 폴백으로 **보고서 출력**(서비스 중단 없음)

넣을 그림: `docs/ARCHITECTURE.md` 1절의 흐름도를 도식으로 다시 그리기 (도구 4개가 병렬로 → report로 모임, 검증 루프 화살표)

### ④ AI 기술·Tool/API 구성 (Agent 구성·설계 25점)
양식 요구: 모델, Framework, RAG·Memory, Tool/API의 역할·입출력·호출 조건, **오류·환각 대응, 근거·출처 표시, 재시도·예외 처리**.

초안
- **모델**: Anthropic Claude API. 두 곳에서만 사용 — (a) 문장 → JSON 스키마를 강제한 구조화 추출 (b) 점검 결과 요약
- **Framework**: MVP는 Python 함수 오케스트레이션(의존성 최소). 본선에서 LangGraph로 이관 — 각 점검 도구 = 노드, 요약 검증 실패 → 재작성은 조건부 엣지
- **RAG**: 규정을 **조문 단위**(rule_id·원문·범주·수치 파라미터)로 저장 → 점검 범주로 검색. 조문 ID를 보존해서 인용 검증에 사용. 조문이 많아지면 임베딩 검색 추가
- **Memory**: 담당자 보유 종목 DB, 데이터 기준일 기록(manifest), (확장) 점검 이력
- **Tool 구성**

  | Tool | 역할 | 입력 | 출력 | 호출 조건 |
  |---|---|---|---|---|
  | intake | 문장 → 투자안 구조화 | 자유 문장/폼 | Proposal | 항상 (자유 문장일 때만 LLM) |
  | rules | 조문 조회·실존 확인 | 범주 / rule_id | 조문 원문 | 점검·검증 시 |
  | exclusion | 배제목록·배제 테마 대조 | 기업명·섹터 | 신호 + 목록 행 + 조문 | 항상 |
  | sanctions | 제재목록 대조 | 기업명 | 신호 + 목록 행 + 조문 | 항상 |
  | limits | 투자 전후 비중 계산 | 종목·금액·보유내역 | 신호 + 계산식 | 항상 |
  | conflicts | 담당자 보유 대조 | 담당자 ID·종목 | 신호 + 보유 내역 | 항상 |
  | report | 종합·요약·검증 | 점검 결과 전체 | 보고서 | 마지막 |

- **신뢰성 확보**
  - 환각 대응: 요약의 `[IG-x-x]`가 규정 DB에 실재하고 이번 근거에 쓰였는지 + 숫자가 근거에 있는지 검사 → 최대 2회 재작성 → 템플릿 대체
  - 근거·출처: 모든 신호에 근거(조문 원문·목록 행·계산식) 첨부, 보고서 하단에 데이터 파일·기준일·실데이터 여부 표시
  - 재시도·예외: LLM 호출 실패·거절 시 폴백, 파일 누락 시 명확한 오류, 판정 불가는 UNKNOWN + 사유
  - 오탐 방지: "Southern Co(석탄)"와 "Southern Copper(구리)"처럼 이름 일부만 같은 경우 RED가 아니라 "동일 기업인지 확인" 질문으로

### ⑥ MVP 개발 계획 (실현 가능성 20점)
양식 요구: 본선 기간 내 MVP 범위·핵심 기능, 기술 스택, 단계별 일정·완료 기준, 데모 시나리오, 리스크와 대응.

초안
- **이미 동작하는 프로토타입이 있음** ← 가장 큰 강점. 화면 캡처 2장(시나리오 1·2) 넣기
  - 점검 4종 + 보고서 + 모드 B + Streamlit 화면 + 자동 테스트 49개 (샘플 데이터 기준)
- **범위**: 상장주식 단일 투자안(모드 A) + 포트폴리오 스크리닝(모드 B). 사모·대체·부동산은 제외
- **스택**: Python, pandas, pydantic, rapidfuzz, Streamlit, Anthropic SDK, GitHub
- **본선 일정(예시 — 본선 기간에 맞춰 조정)**
  1. 실데이터 교체: 13F, NBIM, OFAC, 한국투자공사법 조문
  2. 기능 보강: 미공개정보 확인 질문 + 거래제한 목록, 위탁기관 지침, 모드 B 한도 점검
  3. LangGraph 이관, 데모 배포(URL), 시연영상
- **완료 기준**: 데모 시나리오 3개 자동 테스트 통과 / 1건당 10초 이내 / 모든 RED·YELLOW에 근거
- **데모 시나리오**: (1) 담배 기업 150억 → 배제 RED + 책임투자위원회 심의 (2) 같은 투자안, 해당 종목 보유 담당자 → 이해상충 RED 추가 (3) 포트폴리오 전체 → 담배·석탄 테마별 금액
- **리스크와 대응**

  | 리스크 | 대응 |
  |---|---|
  | 내부 지침·담당자 정보 비공개 | 공개 지침 참고 모의 데이터, 구조는 실제와 동일하게 |
  | 기업명 매칭 오탐·미탐 | 이중 점수 + 애매하면 YELLOW로 사람 확인 |
  | LLM 환각 | 판정에서 LLM 배제 + 요약 검증 |
  | 데이터 최신성 | 기준일·실데이터 여부를 보고서에 표시 |

### ⑦ 기대효과 및 확장성 (활용성·확장성 15점 추정)
양식 요구: 시간·비용·품질·신뢰성 개선, 확장 가능성, 운영 적용 경로.

초안
- **시간**: 여러 부서·자료를 거치던 확인을 1회 실행으로. 프로토타입 측정: 1건 약 0.4초(LLM 미사용), 보유 77종목 일괄 점검 약 1초 — *샘플 데이터 기준*
  - ⚠️ "몇 시간 → 몇 분" 같은 수치는 근거 없이 쓰지 말 것. 쓰려면 "가정"이라고 밝히기
- **품질·신뢰성**: 모든 판정에 근거 100%(시스템이 강제), 같은 입력엔 같은 판정, 판정 이력이 보고서로 남아 사후 설명 가능
- **비용**: 공개 데이터 + 건당 LLM 호출 최대 2회(+검증 재시도)
- **확장**
  - 자산군: 사모·대체·부동산 (1차 회의)
  - 규정 변경 영향 분석: "석탄 기준을 50% → 30%로 바꾸면 영향받는 보유 종목은?" — 기준이 조문 파라미터라 바로 계산 가능
  - 승인 절차: "안내" → 결재 시스템 연동으로 "거쳤는지 확인"
  - 다른 공적 기금(연기금 등)에 규정 DB만 바꿔 적용
- **운영 적용 경로**: ① 준법감시부 사전 점검 보조(파일럿) → ② 분기 포트폴리오 정례 스크리닝 → ③ 결재·주문 시스템 연동

## 3. 심사·상호평가에서 나올 질문과 답

| 질문 | 답 |
|---|---|
| 이거 에이전트 맞나? 규칙 엔진 아닌가? | 규정 준수는 "같은 입력에 같은 판정"이 필수라서 **판정은 도구(코드)에 맡기고**, Agent는 입력 해석·계획·도구 실행·검증·질문을 담당하도록 설계. 정보가 부족하면 스스로 멈추고 묻고, 요약이 틀리면 스스로 고쳐 씀 |
| 왜 멀티 에이전트 토론 구조가 아닌가? | 컴플라이언스에서 에이전트끼리 토론해 결론이 바뀌면 재현성·설명 책임이 떨어짐. 대신 점검 도구를 독립적으로 두고 결과를 규칙으로 합침 |
| LLM이 틀리면? | LLM은 판정을 못 바꿈. 요약에 없는 조항·숫자가 나오면 자동 차단 |
| 내부 지침은 비공개인데 어떻게? | 공개된 NBIM·국민연금 지침을 참고해 모의 작성. 실제 도입 시 조문 파일만 교체 |
| 1.26조 지적이랑 무슨 관계? | 같은 공개 데이터(13F + 공개 배제목록)로 분기마다 돌렸다면 사전에 보였을 숫자 → 모드 B (본선에서 실데이터로 검증) |
| 사람 일자리를 없애나? | 최종 판단은 사람. 반복 대조를 줄이고 판단에 집중하게 함 |

## 4. 시간이 있으면 보완할 것 (우선순위)

예선은 **기획서만** 내므로 코드 수정은 필수 아님. 기획서에 "계획"으로 쓰면 충분.

1. **(기획서)** ⚠️ 표현 수정 5가지(1절) — 사실관계 오류는 상호평가·전문가 평가 모두에서 감점 요인
2. **(기획서)** ③에 자율 범위표·종료 조건 — 배점 1위 항목의 양식 요구 그대로
3. **(코드, 30분)** 모드 B에 단일종목 한도 점검 추가 → 1차 회의 "주기적으로 비율 초과 잡기" 충족
4. **(코드, 30분)** 미공개 중요정보 확인 질문 + 거래제한 목록 대조 → 3차 회의 항목 충족
5. **(본선)** 실데이터 교체, 법령 조문 입력, LangGraph 이관, 데모 배포
